Part 3 · Choosing when to retry

Can a model decide when a retry is worth it?

Part 2 showed that a blind retry helps on some tasks and hurts on others. This part asks whether a small learned model can choose, at the very first alarm, between retrying and carrying on.

The headline numbers, on 1,000 test runs
+2.1 ppsuccess over doing nothing (70.6% against 68.5%)[+0.4, +3.9]
9.2%of runs retried, against 34.8% for always retrying
39 / 18runs rescued / runs hurt, against 65 / 42 for always retrying

What we built

A model with two heads: one estimates how likely success is if we retry, the other if we carry on. At the first alarm it looks at the alarm signals, the gripper state, which task this is, and DeltaDINO’s score, then picks the better option.

It was trained on 218 alarm cases, where we ran each situation 4 times with a retry and 4 times carrying on, each with fresh randomness. It was frozen before any tuning or test run.

Try it: retry, continue, or choose

Always continue: pause only, then carry on. Always retry: rewind the arm and retry once at the first alarm. It does not flag by choice; it flags only when the rewind itself is invalid, meaning the restored arm would sit more than 1 cm inside an object. That stopped and flagged 1.4% of runs. Variants: the same model using only the task id, or without the camera score, or also allowed to flag a human. Only the task-id variant was formally compared with the selector (test H3, below).

What we learned

  • The selector is a more cautious retry, not a smarter one. It retries far less often yet ends up with similar net gains, so it picks its moments but not better than a simple rule.
  • The camera score adds nothing: the variant without it did no better or worse (71.5% against 70.6%). That difference was not tested, and the confidence intervals overlap widely.
  • A model that knows only the task id did as well as the selector: the pre-registered test of the selector against it (H3) was not supported (−0.9 pp).
